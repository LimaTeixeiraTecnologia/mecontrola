- Falha de download/STT/validação não permite replay automático do mesmo WAMID -> comprovado: `TestAudioAuditIntegrationSuite/TestInsertTerminalRejectedNeverReprocessed_RF22` insere um outcome terminal `rejected` e tenta uma segunda gravação com `approved` para o mesmo wamid; a segunda chamada retorna `ErrAudioAuditAlreadyExists` e `FindByWAMID` confirma que o outcome original `rejected` nunca foi sobrescrito — nenhum `dedup.Delete` é chamado pelo repository (não existe esse método na sua superfície).

## Suposições
- O DDL da tabela reproduz literalmente o que a techspec propõe em "Persistencia de Auditoria" (`.specs/prd-agente-audio-openrouter/techspec.md:320-339`), incluindo `outcome`/`reason` `NOT NULL` sem estado "pending" — por isso `InsertTerminal` sempre grava um registro com outcome já decidido (nunca uma linha "em progresso"); a ordem exata de quando o consumer chama `InsertTerminal` em relação ao download (antes/depois) é responsabilidade de orquestração da tarefa 6.0 ("Integração consumer, outbox e wiring Mastra"), fora do escopo desta tarefa que só entrega o contrato do repository.
- `UpdateOutcome` foi adicionado para cobrir a subtarefa 5.3 ("insert terminal por WAMID **e update transacional curto**") modelando a transição `AudioOutcomeApproved -> AudioOutcomeDispatched` (o outcome `dispatched` só é atingível depois que `HandleInbound` roda com sucesso, o que acontece depois do insert terminal de aprovação) — é a única transição de outcome permitida pelo contrato; falhas técnicas (`rejected`/`transcription_uncertain`/`transcription_failed`) são gravadas diretamente como terminais via `InsertTerminal`, sem update subsequente, preservando "não chamar dedup.Delete" e "sem replay automático" (RF-22/RF-23).
- O CHECK de `reason` mirra exclusivamente os 7 valores hoje definidos em `usecases.AudioReason` (tarefa 4.0), que cobrem apenas razões de classificação técnica de transcrição (STT/idioma/confiança/incoerência). A techspec também menciona razões de rejeição pré-STT (tamanho, duração, custo) que pertencem às tarefas 1.0/2.0/6.0 e ainda não têm constante Go correspondente; ampliar o CHECK para essas razões é responsabilidade de uma migration adicional quando essas constantes forem introduzidas (instrução explícita do orquestrador: "consuma os tipos/outcomes fechados do decisor (tarefa 4.0) para os CHECK constraints").
- `Peer`/`MediaID` são persistidos na tabela para auditoria/troubleshooting (RF-25/RF-26), mas o repository nunca os expõe como métrica ou label — não há nenhuma chamada de métrica neste arquivo; a garantia de baixa cardinalidade nas métricas de áudio (RF-28) é responsabilidade da tarefa 7.0.

## Riscos Residuais
- `AudioOutcomeDispatched` ainda não é produzido por nenhum caller real (a tarefa 6.0 é quem vai chamar `UpdateOutcome` após `HandleInbound` bem-sucedido); esta tarefa comprova apenas que a transição é suportada e testada no nível do repository/Postgres, não a integração ponta a ponta.
- O CHECK de `reason` precisará de uma migration adicional (`ALTER TABLE ... DROP CONSTRAINT ... ADD CONSTRAINT ...`, padrão já usado em `migrations/000008_auth_events_resolve_path.up.sql`) quando as tarefas 1.0/2.0/6.0 introduzirem razões de rejeição pré-STT (tamanho, duração, custo, formato); até lá, tentar persistir essas razões falhará no banco por design (fail-closed), o que é o comportamento correto, mas exige que a tarefa 6.0 não esqueça de ampliar o CHECK antes de emitir essas razões.
- Ambiente de execução usou Docker Desktop local (testcontainers `pgvector/pgvector:pg16`) — a mesma suíte deve ser revalidada no runner de CI antes do merge para garantir que a imagem/rede do pipeline também sobe o Postgres 16 sem diferença de comportamento.
