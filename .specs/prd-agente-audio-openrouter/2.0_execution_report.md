### Achados da Revisão

- [medium] `internal/platform/whatsapp/media/client.go` — `VerifyChecksum` é uma função separada de `Download`, não invocada automaticamente dentro do fluxo de download. Isso segue literalmente a assinatura `Download(ctx, url, maxBytes)` definida na techspec (sem parâmetro de SHA esperado), mas exige que o consumidor (tarefa 6.0) chame `Resolve -> Download -> VerifyChecksum` na ordem correta. Risco residual documentado; não bloqueante para esta tarefa porque a capacidade está implementada e testada, e a orquestração é escopo de 6.0.
- [low] `internal/platform/whatsapp/media/client.go` — `Resolve` não valida o formato do `mediaID` além de checar vazio (sem regex/charset). Aceitável porque o payload já é validado a montante pela tarefa 1.0 (parser tipado); registrado como defesa em profundidade não aplicada.
- [low] `internal/platform/whatsapp/media/client.go` — `DownloadedMedia.MimeType` usa `resp.Header.Get("Content-Type")` sem normalizar parâmetros (`; charset=...`); consumidor deve usar `MediaDescriptor.MimeType` (da Meta) como fonte primária de MIME, não o header de download.

Nenhum achado `critical` ou `high`. Sem tag `[critical]`/`[security]`/`[blocker]`/`[high]` nos remarks acima — segue para Etapa 5 (persistência de evidências) conforme regra de mapeamento de veredito do `execute-task`.

## Suposições
- O MIME real observado em produção (`.specs/prd-agente-audio-openrouter/whatsapp-audio-payload-evidence-2026-08-04.md`) é `audio/ogg; codecs=opus`; o parser Ogg/Opus foi validado com fixture sintética determinística (sem dependência externa), pois não há arquivo de áudio real no repositório para uso em teste unitário.
- Não há fixture real de M4A/AAC no repositório (WhatsApp em produção só emitiu `audio/ogg`); a task file autoriza teste "quando fixture existir" — foi construída fixture sintética mínima (ISO-BMFF `ftyp+moov+mvhd` e frame ADTS bruto) para validar o parser de forma determinística e auditável, sem depender de codec real.
- `AGENT_AUDIO_MAX_BYTES` e `AGENT_AUDIO_MAX_DURATION` não são lidos por este pacote (não fazem parte do escopo 2.0 — wiring de configuração é tarefa 7.0); `Download` e `CheckMaxDuration` recebem os limites como parâmetro, permitindo que o consumidor aplique os valores de config quando disponíveis.
- Zero dependências novas foram adicionadas ao `go.mod` — os parsers Ogg/Opus e ISO-BMFF/ADTS foram implementados com a stdlib (`encoding/binary`), atendendo à recomendação da techspec de "menor dependência auditável possível".

## Riscos Residuais
- A ordem `Resolve -> Download -> VerifyChecksum -> DetermineDuration -> CheckMaxDuration` antes do STT depende da orquestração da tarefa 6.0 (consumer/workflow); este pacote fornece os blocos, não a garantia de sequenciamento fail-closed em produção.
- O parser ADTS/AAC aceita o primeiro conjunto de frames válidos e para no primeiro frame corrompido, retornando duração parcial em vez de erro, caso pelo menos um frame válido tenha sido lido antes da corrupção. Isso é um trade-off documentado de robustez determinística sem dependência externa; se a Meta um dia enviar `audio/aac` real, recomienda-se revisão adicional com amostra real (hoje só há evidência real de `audio/ogg`).
- `RF-06`/`RF-08` foram cobertos com evidência de teste sintética (servidor HTTP fake); não houve teste real contra a Meta Media API nesta tarefa (não exigido pela task file 2.0 — testes reais ficam sob flag em tarefas posteriores conforme RF-36).
